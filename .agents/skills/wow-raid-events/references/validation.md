# Validation

## Timeline

Check key boundaries, clock conversions, unique spawn identity, chain pulls, target origin, phase windows, player access, Bloodlust and confidence. Compare generated starts/ends against the ledger. Distinct lifetimes must not be merged merely for a cleaner profile.

## Configuration

Inspect the expanded input: style precedes events, appends do not overwrite the route, starts are finite when intended, duration bounds are valid, bosses are classified from evidence, and baseline infrastructure creates no fictitious damage. Check actual target counts and event order, not just the requested counts. Account for jitter in approximate mode.

## Execution and reports

Run a compatible parser/smoke check and inspect warnings. Confirm the intended player, gear, talents, actions and event settings were used. Then inspect a debug timeline and the statistical series appropriate to the metric. Preserve commands, exit status, logs and reports. Compare target-specific damage, active time and owner/action/result scopes.

Label artifacts as teaching overlay, parsing checked, simulated or historical observation. A Python unit test or source-reading pass does not validate an encounter in SimC. Do not publish untested syntax as a working profile. See [scripts](tools-and-examples.md), [reproductions](minimal-repros.md) and [source audit](source-audit-2026-10-06.md).
